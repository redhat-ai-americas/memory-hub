# RBAC and Authentication Guide

A developer-facing reference for MemoryHub's authentication and authorization model. Covers how callers authenticate, what scopes control, and how visibility works in practice.

For the internal design rationale and enforcement implementation, see [authorization.md](authorization.md) and [governance.md](../design/governance.md). For the operational runbook on adding users, see [add-mcp-api-user.md](../runbooks/add-mcp-api-user.md).

## Two ways to authenticate

MemoryHub supports two authentication methods. They produce the same internal identity and use the same authorization rules. Pick whichever fits your deployment.

### API key (`register_session`)

The simpler path. The caller sends an API key at session start; the MCP server looks it up in the `memoryhub-users` ConfigMap and establishes a session.

```
Agent starts conversation
  -> calls register_session(api_key="mh-dev-a76f...")
  -> server looks up key in users ConfigMap
  -> session established: user_id=wjackson, scopes=[user, project, ...]
  -> all subsequent tool calls use this identity
```

The API key is both the credential and the identifier. One key per user. The session lives as long as the MCP connection. No token refresh, no expiration.

**When to use:** development, single-operator clusters, MCP clients that lack native OAuth (Claude Code, OpenClaw).

### OAuth 2.1 (`client_credentials`)

The production path. The caller authenticates against the `memoryhub-auth` service, gets a short-lived JWT, and presents it on every request.

```
Agent starts
  -> POST /token to memoryhub-auth with client_id + client_secret
  -> receives JWT (5-15 min TTL) containing sub, scopes, tenant_id
  -> presents JWT as Authorization: Bearer on every MCP tool call
  -> memoryhub-auth issues refresh tokens for long-running sessions
```

The `client_id` is the agent's registered identity. The `client_secret` is the credential used to obtain tokens. Neither is sent to the MCP server directly; the MCP server sees only the signed JWT.

**When to use:** production multi-tenant deployments, browser-facing apps, anywhere you need token expiration, refresh, and revocation.

### API key vs. client secret: what's the difference?

| | API key | Client secret |
|---|---|---|
| **What it is** | Static bearer token stored in the users ConfigMap | OAuth credential stored in the auth service database |
| **Where it's used** | Sent directly to the MCP server via `register_session` | Sent to `memoryhub-auth` to obtain a JWT |
| **Format** | `mh-dev-<hex>` | Generated by `memoryhub admin create-agent` |
| **Expiration** | Never (lives until rotated or removed) | Never, but the JWTs it produces expire in 5-15 min |
| **Storage** | ConfigMap (plaintext) | Auth service database (hashed) |
| **Rotation** | Edit ConfigMap, restart MCP deployment | `memoryhub admin rotate-secret` |
| **Who has one** | Every user in users.json | Every OAuth client created via admin API |
| **Do you need both?** | No. Use one or the other. | |

Most developer setups use API keys only. The `client_secret` matters when you're using the SDK in OAuth mode (`MemoryHubClient(url=..., auth_url=..., client_id=..., client_secret=...)`), deploying a dashboard, or running in a production multi-tenant environment.

The two methods coexist. The MCP server accepts both JWT-authenticated requests and `register_session` API key calls. You can migrate incrementally.

## What scopes control

Scopes determine two things: which **operations** you can perform (read, write, admin) and which **tiers of memory** you can access. The scopes array in `users.json` lists tier names:

```json
{
  "user_id": "dr-bob",
  "scopes": ["user", "project", "organizational"]
}
```

Internally, each tier name expands into operational scopes. `"user"` becomes `memory:read:user` and `memory:write:user`. A user with all five tier names gets the blanket `memory:read` and `memory:write` scopes.

### Visibility rules per tier

Scopes do not grant blanket visibility. Each tier has its own rule for whose data you can see:

| Tier | Read visibility | Write access | Notes |
|---|---|---|---|
| `user` | **Your own memories only.** `owner_id` must match your `user_id`. No override, even with all scopes. | Your own only | The most restricted tier. |
| `project` | **Projects you're a member of.** Checked via `project_memberships` in your user record. | Projects you're a member of | Feature-flagged via `MEMORYHUB_PROJECT_ISOLATION_ENABLED` (default: on) |
| `role` | **Roles you hold.** Checked via `role_assignments`. | Service agents only (`identity_type: service`) | Regular users can read role memories but not write them |
| `organizational` | **All org-scoped memories in your tenant.** No owner filter. | Service agents only | Shared by design within the tenant |
| `enterprise` | **All enterprise-scoped memories in your tenant.** No owner filter. | **Blocked.** Requires human-in-the-loop approval workflow. | Policy-level; not writable by agents |

### Common misconception: "all scopes = see everything"

Having all five tier scopes does NOT let you see another user's user-scoped memories. The visibility rule for the `user` tier is hardcoded: `owner_id == caller`. This was verified by a live test (2026-08-04) where a user with all scopes searched for and tried to directly read another user's memory. The search returned zero matches and the direct read returned "Not authorized."

### Tenant isolation

Tenant isolation is absolute and checked before any scope logic. Tenants are the hard boundary. A user in tenant A cannot see, search for, or read any memory in tenant B, regardless of scopes. Cross-tenant access attempts return `MemoryNotFoundError` indistinguishable from "that memory doesn't exist." No information about other tenants' data is leaked.

All users in the default `memoryhub-users` ConfigMap share a single `default` tenant. Multi-tenant setups require explicit `tenant_id` assignment per user.

### The admin scope

`memory:admin` is a separate scope not included in any default user configuration. It bypasses per-user ownership within a tenant, allowing admin operations like cross-user search and memory quarantine. Cross-tenant admin access requires an additional `memory:admin:cross_tenant` scope.

Admin operations use the `admin_memory` tool, not the regular `memory` tool. Regular tools always enforce per-user visibility regardless of whether the caller has admin scope.

## User record reference

Each entry in the `memoryhub-users` ConfigMap:

```json
{
  "user_id": "dr-bob",
  "name": "Dr. Bob Smith",
  "api_key": "mh-dev-<hex>",
  "tenant_id": "default",
  "scopes": ["user", "project"],
  "identity_type": "user",
  "project_memberships": ["cardiology-notes"]
}
```

| Field | Required | Default | Description |
|---|---|---|---|
| `user_id` | yes | | Short identifier. Used as `owner_id` on memories, as `actor_id` in audit logs. |
| `name` | yes | | Human-readable label. |
| `api_key` | yes | | Bearer token for `register_session`. Format: `mh-dev-<hex>`. Generate with `openssl rand -hex 8`. |
| `tenant_id` | no | `default` | Multi-tenant isolation key. |
| `scopes` | yes | | Array of tier names. Common values: `["user", "project"]` for agents, `["user", "project", "role", "organizational", "enterprise"]` for operators. |
| `identity_type` | no | `user` | Set to `service` for autonomous agents (curator, compliance scanner) that need to write to `organizational` or `role` tiers. |
| `project_memberships` | no | `[]` | List of project IDs this user can access for project-scoped memories. |

## Practical scenarios

### Single developer, one agent

The simplest setup. One user in the ConfigMap, all tiers.

```json
{
  "users": [
    {
      "user_id": "wes",
      "name": "Wes",
      "api_key": "mh-dev-<hex>",
      "scopes": ["user", "project", "organizational", "enterprise"]
    }
  ]
}
```

Everything is readable and writable (except enterprise, which is read-only by design).

### Multiple developers, same cluster

Each developer gets their own user record with a distinct API key. User-scoped memories are isolated by default. Organizational and enterprise memories are shared.

```json
{
  "users": [
    {
      "user_id": "dr-bob",
      "name": "Dr. Bob",
      "api_key": "mh-dev-<bob-hex>",
      "scopes": ["user", "project"],
      "project_memberships": ["cardiology"]
    },
    {
      "user_id": "dr-alice",
      "name": "Dr. Alice",
      "api_key": "mh-dev-<alice-hex>",
      "scopes": ["user", "project"],
      "project_memberships": ["radiology"]
    }
  ]
}
```

Bob cannot see Alice's user-scoped memories. Bob cannot see radiology project memories. Both can see organizational memories if they have the `organizational` scope.

### Service agent (curator)

A service agent that reads across all scopes but only writes to organizational and role tiers:

```json
{
  "user_id": "curator-agent",
  "name": "Curator Agent",
  "api_key": "mh-dev-<hex>",
  "scopes": ["user", "project", "organizational", "role"],
  "identity_type": "service"
}
```

The `identity_type: service` is what allows writes to `organizational` and `role` tiers. Regular users are blocked from those writes.

## Troubleshooting

**"All memories show up as the same user."** Both agents are using the same API key. Each developer needs a distinct key in the ConfigMap mapping to a distinct `user_id`. See #492 for per-project identity routing.

**"I can't see my colleague's memories."** This is expected for user-scoped memories. User-scope isolation is absolute. If you need shared visibility, write to `project` scope (with shared `project_memberships`) or `organizational` scope (visible to everyone in the tenant).

**"I get 'Not authorized to read memory' on a direct read."** The memory belongs to a different user or project you're not a member of. The server returns the same error for "exists but you can't see it" and "doesn't exist" to avoid leaking existence information.

**"My API key is rejected after a redeployment."** The ConfigMap may have been regenerated from the template, which doesn't include your key. Check `oc get configmap memoryhub-users --context mcp-rhoai -n memory-hub-mcp -o jsonpath='{.data.users\.json}'` and re-add your user if missing. Then restart the deployment.
